# 网页参照器（`harmonica.html`）

自己搭的一台**网页口琴**，用途只有一个：**给"键位映射"一个能被验证的参照系。**

---

## 它解决的是哪个问题

整条链路里最要紧、也最没法求证的一环是这段：

```
我们发：SendInput + 扫描码
   ↓  （Windows 输入栈）
游戏收：浏览器的 KeyboardEvent.code   ← 原程序整套设计都押在这里
```

原程序**不用虚拟键码而是发扫描码**，注释里写明理由是"游戏读 `e.code`（物理位置）"。
但这件事**从来没有被端到端验证过** —— 因为游戏那边我们看不见。

浏览器看得见。所以：

> 让我们的自动演奏器对着这个网页弹一遍，
> 把网页**实际收到**的 `e.code` 序列录下来，和**我们该发的**序列逐条对。
> 对上了 = 扫描码那条路是对的。

**这是唯一能把"发出去"和"收到"对上账的办法。**

---

## 能证明什么 / 不能证明什么

| | |
|---|---|
| ✅ **能证明** | 扫描码 → 浏览器 `e.code` 的映射正确；孔位与移调算得对；事件顺序正确；时序大致准（能看出偏差量级） |
| ✅ **能证明** | 整条"乐谱 → 音高 → 键位 → 输入事件"的链路端到端跑得通 |
| ❌ **不能证明** | **《三角洲行动》本体的键位**。这个页面用的是我们自己的映射（内容来自原程序实测常量 + 我们复刻的算法）。它只是**我们自己的参照系**，不代表正式游戏 |
| ❌ **不能证明** | 正式游戏会不会接收合成输入（那是反作弊的问题，不是映射的问题） |

**用它的另一个好处**：这是本机网页，**没有反作弊、没有封号风险** ——
可以随便测、随便弹、随便让它报错。

## 怎么用（三步）

**① 打开页面并给它焦点**

用浏览器打开 `harmonica.html`，**点一下页面** —— 浏览器只给有焦点的页面投递键盘事件，
而且音频要有一次用户交互才能播。页面右上角会显示「窗口已聚焦」。

**② 正式演奏一下**

保持页面在前台（别切窗口），在终端跑：

```bash
python -m hca.cli --song 诀别书 --engine reference    # 走旧内核，最接近原程序行为
```

也可以直接用旧的 `口琴自动演奏器.exe` 弹 —— 两者应该产生同一条事件流。

页面会实时显示每个音的「按了哪个键 → 哪个孔 → 实际音高」，并记录全部事件。
（想安静测就把「声音」关掉。）

**③ 对账**

点「开始录制」→ 跑演奏 → 点「停止录制」→「复制录制结果」→ 存成 `rec.json`：

```bash
python verify/web_conformance.py rec.json 动作表.json
```

动作表可以直接用旧内核导出的那份：
`.workbuddy/analysis/golden_actions.json`（是个字典，用 `--song "曲名.mid"` 指定一首）。

输出示例：

```
✔ 顺序完全一致：26 个输入事件逐个对上。
  → 说明「键盘字符 → 扫描码 → 浏览器 e.code」这条链完全正确。

时刻偏移（浏览器投递延迟已扣除基准）：平均 -3 ms，最大 12 ms
```

不一致时会指出**第几个事件**、期望什么、实际收到什么。

> 时刻只做参考对比，不判死线 —— 浏览器定时器精度和我们的调度轮询都会带来抖动。
> **顺序**才是硬指标：顺序错就是映射错。

## 页面上的其他东西

| 元素 | 说明 |
|---|---|
| 10 个孔的格子 | 按下哪个键哪个格子亮；孔 9/10 标「无键位」（原程序按不出来，会跳过） |
| `浏览器 e.code` | **最重要的一栏** —— 验证的就是它 |
| 当前移调 | 鼠标键组合算出来的半音数；非法组合会显示"不发声" |
| 可替换的映射 JSON | 把 `mapping/*.json` 的内容粘进去点「应用」，页面就按新映射工作（存 localStorage） |
| 音域信息 | 实时算出"键盘够得到的音域"，应显示 **48~85**，与原程序实测值一致 |

## 一个诚实的提醒

这个页面**不能**用来替代"在真实环境里试一次"。它的意义是：
**把我们能控制的那一半（发送侧）验证到死**，
把"不确定"压缩到只剩"游戏侧收不收"这一件事上 —— 而那件事，任何在自己机器上的测试都回答不了。
